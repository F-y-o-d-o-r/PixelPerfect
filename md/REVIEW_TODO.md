## 1. Критичные технические риски (🔴)

### 1.1 Картинка-оверлей может быть заблокирована CSP страницы
- **Проблема:** если `<img src="blob:/data:">` вставляется в DOM страницы (даже внутри Shadow DOM), директива `img-src` в CSP сайта (GitHub, банки, многие enterprise-стейджинги) может её запретить. Это самый частый сценарий у верстальщиков, работающих с корпоративными стендами.
- **Что делать:** проверить в спайке. Варианты: рендерить макет через `<canvas>` (`createImageBitmap` → `drawImage`, CSP на canvas не влияет), либо `chrome-extension://` URL через `web_accessible_resources` (ограничен тем же CSP — проверить).
- [ ] Выбрать способ рендера оверлея и записать в `PLAN.md` (раздел 3).

### 1.2 Хранилище: `chrome.storage.local` — неподходящее место для картинок
- **Проблема:** в `PLAN.md` и `AGENTS.md` макеты лежат в `chrome.storage.local`. Квота по умолчанию ~10 МБ (без `unlimitedStorage`), данные хранятся как JSON → картинки в base64 (+33%), каждый `get` тянет всё в память. 9 слоёв Retina-макетов легко превысят лимит.
- **Что делать:** картинки (Blob) → **IndexedDB** (через `idb`/`dexie`), в `chrome.storage.local` — только метаданные (позиция, opacity, привязки URL, ссылка на blob-id). Добавить `unlimitedStorage` в permissions на крайний случай.
- [ ] Спроектировать схему IndexedDB (stores: `layers`, `blobs`, `folders`) и миграции версий.
- [ ] Обновить `AGENTS.md` (раздел «Хранение данных») и `PLAN.md`.

### 1.3 Два форм-фактора (плавающее окно + боковая панель) = два UI и два состояния
- **Проблема:** в плане заявлено «плавающее окно **и** Chrome Side Panel». Side Panel — отдельный документ без доступа к DOM страницы и к keyboard-событиям страницы. Фактически это два приложения, синхронизация состояния между ними, двойные баги, двойное тестирование. Vim-режим в Side Panel не работает (фокус не на странице).
- **Что делать:** для MVP оставить **только плавающее окно**. Side Panel — Phase 2, если вообще нужен. Убрать из Спринта 1 `sidepanel/` и разрешение `sidePanel`.
- [ ] Принять решение: MVP = только плавающее окно. Обновить структуру в `PLAN.md` (раздел 3) и чеклист Спринта 1.
- [ ] Если Side Panel остаётся — описать единый источник истины (`chrome.storage` + `onChanged`) и что работает/не работает в панели.

### 1.4 Размер и изоляция Vue внутри content script
- **Проблема:** монтировать Vue-приложение в Shadow DOM на каждой странице — это вес бандла (Vue ~35–50 КБ gz + стили) на **каждой** вкладке при `<all_urls>`. Plus: `<style lang="sass">` в SFC по умолчанию инжектится в `document.head`, а не в shadow root — стили не попадут внутрь. Нужна ручная инъекция CSS в shadow root (`?inline`-импорт или `vite-plugin-css-injected-by-js` с таргетом на shadow).
- **Что делать:** (а) инжектить content script лениво — по клику на иконку / по хоткею (`chrome.scripting.executeScript` + `activeTab`), а не `<all_urls>` на каждой странице; (б) явно решить способ подключения стилей в shadow root; (в) оценить Vue vs Preact/vanilla для плавающего окна (размер, скорость старта).
- [ ] Решить стратегию инъекции (on-demand vs always-on) — это влияет на permissions и на ревью в Chrome Web Store.
- [ ] Прописать в `PLAN.md`, как Sass попадает в shadow root.

### 1.5 Permissions и ревью Chrome Web Store
- **Проблема:** `host_permissions: <all_urls>` + `tabs` + `scripting` — частая причина долгого ревью и отказов («broad host permissions»). Кроме того, `PLAN.md` (Спринт 1) указывает `activeTab`, а в резюме решений — `tabs`+`<all_urls>`: **противоречие**.
- **Что делать:** по умолчанию — `activeTab` + `scripting` + on-demand инъекция. `<all_urls>` / optional host permissions запрашивать, только если нужна авто-активация макетов при навигации (привязка к URL). Использовать `optional_host_permissions` + `chrome.permissions.request` (из user gesture!).
- [ ] Определить минимальный набор permissions под MVP и подготовить текст обоснования для каждого.
- [ ] Устранить противоречие в Спринте 1 (`activeTab` vs `tabs`).

## 2. Важные проблемы дизайна и UX (🟠)

### 2.1 Vim-режим: конфликты с реальными страницами
- **Проблема:** глобальный перехват `h/j/k/l/i/x/v/w/b/0/1-9` на странице: (а) конфликтует с собственными хоткеями сайтов (Gmail, GitHub, Notion, YouTube); (б) цифры `1–9`, `0`, `w`, `b`, `v` в Locked-режиме — опасны; (в) события в Shadow DOM ретаргетятся (`event.target` будет хостом) — проверка «фокус в input» должна использовать `event.composedPath()`, а также `isContentEditable`; (г) страница может перехватить событие раньше (нужен `capture: true` на `window`).
- **Что делать:** (1) в Locked-режиме слушать **только** вход (`i`) — остальное не трогать; (2) всё остальное — только в Nudge-режиме; (3) вход в Nudge — через настраиваемый хоткей/кнопку, вариант `Alt+…` как безопасный дефолт; (4) учесть раскладки (RU/другие) — использовать `event.code` (`KeyH`), а не `event.key`, иначе при русской раскладке Vim-клавиши не работают (**частая боль для русскоязычной аудитории**); (5) таблица в `PLAN.md` 2.4 слишком большая для MVP.
- [ ] Сократить MVP-набор клавиш: `i`/`Esc`, `h/j/k/l`, `Shift+hjkl`, `v`(show/hide), `0`(snap). Остальное — позже.
- [ ] Использовать `event.code`; поддержать нерусские/русские раскладки.
- [ ] Пересмотреть конфликт: `x` в таблице — и «разблокировать», и «закрепить»; `H` — и «показ/скрытие» (как «Space или H»), и в Vim `h` = влево. **Неоднозначность хоткеев**, привести к однозначной таблице.
- [ ] Проверить обработку `Escape` — страницы/модалки сайта тоже закрываются по `Esc` (использовать `stopImmediatePropagation` только в Nudge-режиме).

### 2.2 `pointer-events: none` на оверлее vs перетаскивание мышью
- **Проблема:** в Locked оверлей кликабелен-насквозь — ок. Но Nudge «снимает блокировку» и, видимо, позволяет двигать мышью; это нигде не специфицировано. Нужно явно: Nudge = клавиатура (+ опционально drag), и что происходит при клике по странице в Nudge.
- [ ] Уточнить поведение: клик по странице в Nudge-режиме → остаётся Nudge или авто-Lock?

### 2.3 Retina / DPR: «Auto» нечёткое
- **Проблема:** `window.devicePixelRatio` — это про экран, а не про картинку. Макет из Figma может быть экспортирован в 1x или 2x; из ширины файла **нельзя** надёжно понять, 1x это или 2x. Кроме того, `devicePixelRatio` меняется при зуме браузера (Ctrl +/–) — оверлей поплывёт.
- **Что делать:** определять «Auto» эвристикой: сравнить ширину картинки с `window.innerWidth` (если `imageWidth ≈ innerWidth × DPR` → 2x), хранить выбор на слой; на `resize`/смену зума пересчитывать. Для вставки из буфера Figma (2x по умолчанию) — заложить дефолт «2x на Retina».
- [ ] Описать алгоритм Auto в `PLAN.md`; обработать browser zoom.
- [ ] Перенести базовый Retina-тумблер **в MVP (Спринт 2)**: сейчас он в Спринте 3, хотя это одна из ТОП-фич и заявленный UVP.

### 2.4 «Snap to Top-Center» — формула неверна для частых случаев
- **Проблема:** `X = (window.innerWidth − imageWidth) / 2` не учитывает: ширину скроллбара (`documentElement.clientWidth`), макет в 2x (нужна CSS-ширина), `position: absolute` относительно документа vs `fixed` относительно viewport (при скролле).
- [ ] Определить систему координат оверлея: `absolute` в документе (скроллится со страницей — как правило нужно) или `fixed`. Записать это решение.
- [ ] Использовать `clientWidth`, учитывать масштаб слоя.

### 2.5 Привязка к URL: слишком наивная
- **Проблема:** ключ `Origin + Pathname` не покрывает: динамические маршруты (`/product/123`, `/product/456` — один макет), query/hash-маршрутизацию, `localhost:3000` vs `:5173`, `www.` vs без, смену стейджинг-доменов. SPA-навигация: `popstate` недостаточен, `pushState` из изолированного мира content script **не перехватить** патчем (изолированный мир не видит `history` страницы). Правильно: `chrome.webNavigation.onHistoryStateUpdated` из background (нужен permission `webNavigation`) или Navigation API.
- **Что делать:** хранить правила привязки как паттерны (`/product/*`), по умолчанию — точный путь; кнопка «привязать к этому пути / к шаблону / ко всему домену».
- [ ] Спроектировать модель `UrlBinding` (`type: exact | prefix | pattern | domain`).
- [ ] Выбрать механизм детекции SPA-навигации (`webNavigation.onHistoryStateUpdated`).

### 2.6 Лимиты и монетизация: стратегический риск
- **Проблема:** главный современный конкурент (Pixel Perfect Pro, 4.4⭐) позиционируется как **«no ads, free forever, unlimited layers»**. Наш Free-лимит «3 папки × 3 слоя» воспринимается как ограничение при бесплатной альтернативе без лимитов. Плюс этот лимит технически обходится (локальные данные), и вся Supabase/Stripe-инфраструктура в MVP тратит недели на то, что не даёт ценности пользователю.
- **Что делать:** (1) в MVP **не строить** биллинг и Supabase Auth (в `PLAN.md` они уже Спринт 5 — так и держать; не тянуть в Спринт 1–2); (2) лимиты слоёв не навязывать в v1.0 — собрать установки и отзывы; (3) определить, **за что** реально платят (Figma-импорт, Smart Diff, командные пресеты, экспорт отчётов), а не за счётчик слоёв; (4) у `ROADMAP.md` три разных сценария монетизации/бэкенда — свести в один.
- [ ] Определить Free/Pro границу по ценности, а не по счётчику слоёв.
- [ ] Не включать `@supabase/supabase-js` в бандл MVP (вес, лишние permissions `identity`).

### 2.7 Pro-статус и обход проверки
- **Проблема:** статус Pro, проверяемый на клиенте (`is_pro` в `chrome.storage`), тривиально обходится правкой в DevTools. Для расширения это нормально для дешёвой подписки, но нужно осознанно.
- **Что делать:** принять как данность; серверная проверка только для действительно «серверных» фич (Figma-прокси, командные пресеты). Не тратить время на DRM-защиту клиента.
- [ ] Зафиксировать политику: клиентская проверка = «честная лицензия», серверные фичи защищены по JWT.

## 6. Предлагаемый облегчённый MVP (для обсуждения)

1. Content script (on-demand) + Shadow DOM плавающее окно (Mini-bar + Expanded).
2. `Cmd+V` / Upload / Drag&Drop → слой (IndexedDB).
3. Позиция X/Y, opacity, show/hide, lock, Snap Top-Center, Retina 1x/2x/Auto.
4. Vim: `i` / `Esc` / `hjkl` / `Shift+hjkl` (через `event.code`).
5. Привязка к странице (exact path) + простая папка (без лимитов).
6. Без: Supabase, оплаты, Side Panel, Smart Diff, брейкпоинты, стеклянное окно настроек.
